## 문제의 증거와 설계 결정

1. TSLA 장기 증액 질문이 1시간 차트로 요약됐고 Cybercab을 보안 사건으로 오해했다. `specialistRoundInput.ts`는 질문과 무관한 역할별 슬롯, 첫 슬롯의 고정 materiality를 사용한다. **조사 명세의 목적·용어·핵심 질문을 공유하고, 해당 질문에 맞춰 역할 내 슬롯 우선순위를 정한다.** 캐릭터와 전체/개별팀 실행은 유지한다.
2. `specialistRoundSqliteStage.ts`의 `filingExcerpt`는 첫 12,000자를 먼저 넣고 최대 12,000자로 자른다. 뒤의 주제별 본문 창이 사실상 사라진다. **본문 전체에서 질문과 역할에 맞는 구간을 선택하고 위치를 보존한다.** 숫자 레지스트리도 기간별 추세가 보이게 묶는다.
3. `initialCollectionData.ts`는 최근 8-K 두 개와 본문만 수집한다. **최근 실적 발표 8-K와 실제 첨부된 실적/주주서한 HTML을 유한한 개수로 추가 수집한다.** 제출 문서에 없는 URL을 만들지 않는다. 기본 공시 수집은 유지하고 추가 자료 실패를 전체 실패로 만들지 않는다.
4. 기존 follow-up 프롬프트는 웹 검색이 가능하다고 하지만 `codexPolicy.ts`는 follow_up을 disabled로 설정한다. **기존 감사 가능한 웹 근거 수집 경로를 연결해 제한된 추가 조사를 실제로 수행한다.** 스냅샷을 몰래 변경하거나 새 검색 결과를 이전 자료로 위장하지 않는다. 운영 데이터/권한 경계는 보존한다.
5. 기존 의미 감사는 주장과 근거 일부만 읽고 원래 질문, 주장별 반대 관찰, 반증 조건을 받지 않는다. **기존 감사 호출에 이 정보를 전달하고, 질문 이탈·주제 오해·논리 방향·비교 기간을 검증한다.** 감사 단계 자체를 중복 신설하지 않는다.
6. 최종 보고서가 숫자를 나열하고 질문을 반복하는 경향이 있다. **동일 기간 추이와 경제적 연결을 제공하고, 실제로 확인된 주장만 최종 편집에 사용한다.** 목표가·확률·투자 수익률은 근거 없이 만들지 않는다.

## 목표 구조와 불변 조건

요청 → 기본 공시/시장 수집 → 근거를 읽은 조사 명세 → 필요한 공시 구간·최신 실적 자료 → 독립 조사 → 팀 합의/핵심 반론 → 제한된 추가 조사 → 의미 감사 → 질문에 대한 답과 근거 중심 발행.

- 조사 명세는 원래 질문, 기간/목적, 핵심 쟁점 3~5개, 주제별 검색어, 근거로 확인된 용어와 미확인 용어를 포함한다. 명세는 사실 원천이 아니며 출처를 대체하지 않는다.
- 질문/명세는 mandate 해시에 포함하고 현재 run에 저장한다. 재개 시 동일한 명세를 읽어야 한다. 기존 저장 보고서와 진행 중 작업의 선택적 필드 호환은 유지한다.
- 용어 확인에는 실제 출처 ID와 원문 인용 구간이 필요하다. 불일치하면 확인된 용어로 채택하지 않는다. 미확인 용어의 의미를 추측해 리스크 분석으로 확장하지 않는다.
- 질문에 맞춰 우선순위를 바꾸되 증거 권한, 역할 소유권, deterministic claim ID, source lineage, 실제 표결을 보존한다.
- 숫자는 기존 typed value registry와 동일 기간/회계 기준을 사용한다. 모델이 만든 임의 숫자를 레지스트리에 등록하지 않는다.
- 새 웹 자료는 기존 attempt web evidence 저장·인용 정책을 따른다. 단순 검색 스니펫을 SEC 원문 검증과 동일 취급하지 않는다.
- 결론을 바꾸는 불확실성이 남으면 그 부분을 명시한다. 모든 결과를 자동으로 ‘대기’ 문장으로 대체하지 않는다.

- 감사 체크포인트: 원래 질문·명세·수정된 최종 주장·반증·반대 관찰을 기존 의미 감사 입력에 추가했다. 개별팀은 합의 단계에 같은 명세와 반증 방향 검토를 전달한다. 팀 합의 검증 실패를 전체 메모 자동 수용으로 바꾸던 fallback을 제거했다. 기존 재시도 경로로 돌린다.
- 계산/화면 범위: 기존 investmentModel의 계산 경로를 유지하고 새 가짜 목표가 모델은 만들지 않았다. 분기/기간별 재무 근거 표를 전문 입력에 추가했다. Q&A 최대 5개·동일 주장 최대 2개, 답변 중복 제거 및 빈칸 채우기 제거. 상단 답→근거→반론→변경 조건과 컨센서스/실적 라벨을 수정했다.
- 모델 비용 결정: 모델 종류는 유지했다. 조사 명세 호출 1회 추가; 합의·의미 감사·최종 편집만 low에서 medium으로 변경해 논리 검토에 추론 여유를 준다. 전문 조사와 follow-up 수의 기존 상한은 유지한다.
- 검사 현황: 새 6개 경계 검사, 전문 입력/슬롯/후속 조사 검사는 통과. Q&A 정책 변경에 따른 정확한 기대값을 갱신했다. 기존 의미 감사 fake가 오래된 바이너리 pin을 쓰던 부분은 현재 검증된 pin으로 맞췄다. 테스트의 고정 2회 재시도 기대와 실제 CALL_BUDGET_POLICY.maxAttemptsPerLogicalArtifact=4 간 불일치가 일부 남아 있으며, 테스트를 통과시키려고 재시도 정책/검증을 완화하지 않는다. 전체 build 및 새 실생성 진행 예정.

- 실생성 1차 시작에서 SEC filings의 새 items 메타데이터가 엄격한 company-facts lineage 계약으로 흘러들어가 invalid_context가 발생했다. 세 요청은 생성 전 수집 단계에서 실패했으며 리서치 생성 수로 세지 않는다. lineage 변환 시 items를 분리하도록 수정하고 새 실행으로 확인한다.

- 실생성 2차에서 재무팀 입력이 264~266KB로 256KiB 한도를 넘어 실행 전 거절됐다. 반복되는 run/snapshot/hash 메타데이터가 레지스트리 입력 213KB를 차지했다. 원본 레지스트리와 검증은 보존하고 모델용 값 투영에서 반복 메타데이터만 제거한다. 숫자·단위·기간·출처·공시·계산식·인용 ID는 유지한다. 실제 명세에서 발견된 ‘최종 판단을 하지 않는다’ 지시와 일반 명사의 불필요한 용어 등록도 공통 planner 지시에서 수정한다.

- MSFT 실제 재시도 4회에서 공시의 Azure 성장률을 등록된 전체 매출 지표에 연결하거나 ID 없이 반복했다. 기존 재시도에는 오류 코드만 있고 거절된 문장이 없었다. 실패한 주장·선택 지표를 현재 attempt에 불변 저장하고 같은 job/run의 직전 실패 본문만 다음 수정 입력에 전달하도록 보강한다. 숫자 검증을 완화하지 않는다. 새 MSFT 요청으로 복구를 확인한다.

- TSLA v3 시장팀 합의는 네 번 중 두 번이 명시적 반론 삭제, 두 번이 전체 주장 분류 누락으로 차단됐다. 기존 자동 수용 fallback을 없애면서 드러난 계약 전달 누락이다. 팀 입력에 주장별 삭제 가능 여부와 정확한 수정 출처 목록을 구조화해 전달한다. 출처/반론 보호를 완화하지 않는다.

- NVDA v3의 마지막 초안은 올바른 현금전환율을 사용했는데 뒤의 ‘매출채권 증가’를 ‘매출 성장’으로 읽은 수치 검증 때문에 거절됐다. 백분율을 문서 전체 키워드와 연결하던 검사를 인접 문장/절의 지표에 연결하고 매출채권을 매출 성장으로 오인하지 않게 수정한다. 같은 오류 수치는 계속 거절하는 회귀 검사를 추가한다.

- TSLA v6 시장 메모는 미등록 10년물 금리로 차단됐다. 실제 Treasury/BLS 자료는 수집하지만 값 레지스트리에 등록하지 않는 전달 누락을 확인했다. 관측일·원래 단위를 보존한 최근 3개 관측치를 정식 등록한다. 지수 수준을 물가 상승률로 바꾸거나 미공개 발표 시간을 만들지 않는다. 마지막 TSLA는 이 경로까지 포함해 재생성한다.

- 마지막 실행 체크포인트: TSLA v7 `37bd12be-2974-4b2d-97e1-2ca3f5ea9452`, snapshot `8c36a4a1-f4ec-4bd7-8748-335dc1a18b62` 생성 중. MSFT v4와 NVDA v6는 발행되어 원문을 읽었다. 워커 v7 도구 세션 8981, 로그 `upgrade-worker-v7.log`; 이전 v6 워커는 정상 종료했다. Node20 워커 빌드/전체 타입 검사와 수집/registry 13검사 통과. 전체 계획의 목표 점수는 아직 달성 판정 전이다.
- 실제 평가에서 확인한 잔여 설계 문제: 개별팀의 publicSummary는 팀 전체 결론이지만 strongestCountercase/falsifier는 서로 다른 개별 주장으로 조립한다. 개별 주장에 대한 반론이 팀 결론의 지지 근거가 되는 경우가 있다. 최종 결론·반론·반전 조건의 동일 판단 대상에 대한 검증을 별도 완료 조건으로 두어야 한다. 현재 원문 MSFT 7/10, NVDA 6.5/10이며 이 한계를 숨기지 않는다.

- P3 추가 구현: 실제 NVDA에서 최종 결론과 개별 반론이 섞이는 문제를 확인하여 같은 팀 합의 호출이 `decisionPacket`(최종 방향, 주 주장 ID, 반론의 근거 주장 ID, 반론, 반전 조건)을 함께 만들게 한다. 새 질문 명세가 있는 작업은 필수, 기존 저장 산출물은 선택 필드로 호환한다. 생존 주장/수정 ID를 인증하고 수치 검증에 새 문장을 포함한다. 개별팀 발행은 해당 묶음을 사용한다. 별도 모델 호출은 늘리지 않는다. NVDA를 네 번째 발행 샘플로 다시 생성해 결과를 확인한다. TSLA v7 진행 작업에는 워커를 중간 교체하지 않는다.

- TSLA v7 발행 후 원문 점검: 질문/제품 이해와 핵심 반증은 개선됐지만, 최종 편집 모델의 내부 JSON 형식 오류로 deterministic fallback이 사용됐다. 원인: transport는 candidateJson만 강제하고 내부 canonical schema를 모델에게 전달하지 않았다. `chairSynthesisV3Prompt`에 실제 스키마를 포함하고 필수 키/객체 형식을 명시한다. 장기 질문의 change_conditions 원문 선택은 사업/현금흐름 조건을 우선하고 1시간 차트 조건에 불이익을 준다. 상단 결론과 본문 변경 조건의 일치도 지시한다. NVDA v8 후 TSLA를 다섯 번째 발행 샘플로 생성한다.

- NVDA v8은 팀 입력 생성 후 제공자의 strict output schema 검사에서 `codex_schema_invalid`로 중단되었다. 저장 호환용 선택 필드를 그대로 모델 스키마로 사용한 것이 원인이다. 새 실행용 스키마는 decisionPacket 필수, 기존 실행용 스키마는 해당 필드를 생략하도록 분리하고 입력 해시/실행 스키마 선택을 일치시켰다. 값 검증을 완화하지 않는다. NVDA v10과 TSLA v9를 마지막 두 발행 샘플로 생성한다.

- 최종 실행 체크포인트: 같은 v10 워커에서 NVDA `dba86fab-3172-461e-890c-804cc8524eb3`(v10 ledger), TSLA `9d142f4b-cfcc-42f4-bcfb-b5ac0910bc19`(v9 ledger)를 생성 중. 워커 세션 26775, 로그 `upgrade-worker-v10.log`. 직전 v8 워커는 종료했다. 개별팀 신규 output schema는 decisionPacket을 필수로 포함하며, 저장 스키마는 호환을 위해 선택 필드다. 최종 팀 검사 27개, chair 검사 15개, v9 전체 빌드, v10 워커 빌드 통과. 기존 실패 실행/보고서는 보존한다.

- NVDA v10 발행 완료: report `635715e8-5f8a-41fb-be59-6e7251ebd4a6`, 원문 평가 6.5/10 유지. 반론 방향은 개선됐으나 falsifier가 최종 결론을 유지하는 조건으로 남았고 계산 소수 노출 문제가 있다. 목표 점수를 충족했다고 선언하지 않는다. 결과 문서에 독립 결론 감사·표시 정밀도·질문별 출력 선택의 정확한 후속 수정 지점과 완료 기준을 기록했다. TSLA v9는 의미 감사 단계다.

- 종료 체크포인트: 최종 TSLA `9d142f4b-cfcc-42f4-bcfb-b5ac0910bc19`, report `11f75b28-b7fc-4d7e-931c-d0fc38a5a836` 발행. 이번 새 발행 총 5개 모두 원문 평가 완료.
