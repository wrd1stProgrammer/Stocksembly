# Production scaling operations

## Capacity and ownership

Normal capacity is one `t3.medium` web and one `t3.large` worker. No second instance is created to attach the existing web or to test this change. A single web still has a brief interruption during in-place deployment or replacement. An ALB cannot make one instance highly available.

The web group `stocksembly-web` uses the existing web instance initially. Its launch template creates a clean Amazon Linux host and obtains private runtime configuration from Secrets Manager, bootstrap scripts from the private artifact bucket, and the last successfully deployed image from `/stocksembly/prod/web/image` in Parameter Store. PostgreSQL and S3 remain authoritative; the old web filesystem is not a dependency. New hosts use SSM; the original SSH/EIP details are only for the retained initial hosts.

`provision-web-autoscaling.py` deliberately starts the group at zero, attaches the existing instance (which increments desired capacity), and then sets minimum one. Setup leaves maximum one and alarm-driven scaling suspended until live verification. The intended enabled policy is minimum/desired one, maximum three, CPU target 35%, five-minute warmup. On a two-vCPU host, one saturated Node.js thread can consume roughly half the host CPU; a 55–70% host-level target would miss that bottleneck. AZ rebalancing stays suspended to avoid unsolicited temporary spare capacity.

The load balancer and ASG are managed by the provisioning scripts, separately from the original foundation CloudFormation stack. The original EIP remains associated for DNS-cache compatibility. Before a future foundation-stack update, reconcile its `SeparateWebInstanceId` / `ApplicationAddress` references if ASG has replaced the original web. Do not use that old parameter to select deployment targets; deployments discover ASG membership.

## Request path

- `stocksembly.com` and `www.stocksembly.com`: Route 53 alias → ACM HTTPS ALB → web nginx port 8080 → Next.js port 3000.
- Static images continue using the existing CloudFront domain.
- Nginx port 8080 accepts network traffic only from the ALB security group; forwarded HTTPS headers and unbuffered event streams are preserved.
- `/api/health` checks the web process. Shared RDS failures should not cause a whole-fleet replacement storm. The target group now checks `/api/health`, and ASG uses ELB health with a 900-second startup grace period.
- Existing direct HTTPS/EIP is temporarily retained for DNS caches. Retire it after delegation caches have expired, rather than breaking cached visitors during migration.

## Releases

Main remains PR-protected. `WEB_ASG_NAME=stocksembly-web` enables instance discovery. SSM deploys one instance at a time and drains ALB targets when more than one is present. A failed command restores target registration. Successful web deployments save their environment to `stocksembly/prod/web-bootstrap`; only after fleet success does CI advance the bootstrap image pointer. No extra instance is launched for deployment.

Workflow dispatch also builds an image artifact without AWS credentials or deployment. Supply an existing static-asset release SHA. This supports a supervised infrastructure cutover without bypassing main's review protection. Image artifacts are retained three days. Ordinary production deployments still build and push on main.

Keep bootstrap writers scoped to the single web configuration secret and deployment object prefix. Never put keys or application secrets in user data, AMIs, repository files, or deployment output.

## Worker preparation

`stocksembly-worker-metrics.timer` runs once per minute. `publish-worker-metrics.sh` reads the existing RDS secret through the instance role, passes it on stdin to a short-lived process in the worker container, and publishes only aggregate numbers. SQL runs in read-only transactions and uses the production `research` schema. No research is generated by monitoring.

CloudWatch namespace `Stocksembly/Research` includes queued research runs, active research runs, oldest queued age, completion sample count, and 24-hour p95 end-to-end duration. The duration includes queue and recovery time; it is not pure model execution time. There is no fabricated zero-duration sample when no report completed. `QueueMetricsHeartbeat` distinguishes missing monitoring from an empty queue.

Worker alarms are observation-only, with actions disabled. Do not scale the current worker runtime by instance count: `runtimeLifecycle.ts` holds a global PostgreSQL advisory lock. Multi-worker activation must first replace that singleton with per-worker liveness, preserve global admission/provider limits, provision model credentials securely, coordinate the briefing worker, and add termination draining. Then calibrate desired capacity using measured waiting time and processing capacity. The current SQS queue is a wake-up signal, not the authoritative backlog.
