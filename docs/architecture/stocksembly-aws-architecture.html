Production Architecture · 2026.07

Stocksembly AWS 운영 아키텍처

미국 주식 리서치 SaaS를 초기 비용은 낮게 유지하면서도 인증, 작업 대기열, 데이터 영속성, 자동 배포를 분리한 현재 운영 구조입니다.

AWS us-east-1 단일 EC2 · Docker 2개 Cognito + PostgreSQL SQS + S3 GitHub Actions + ECR + SSM
한 문장으로 설명하면

사용자의 요청은 Next.js 웹 서버가 인증·소유권을 확인한 뒤 SQS에 등록하고, 별도 리서치 워커가 AI 분석을 수행해 결과와 근거를 PostgreSQL·S3에 영속화하는 구조입니다.

현재 설계 목표

초기 사용량에서는 관리 비용을 최소화하고, 사용량 증가 시 웹·워커·DB를 단계적으로 분리할 수 있도록 경계를 먼저 만든 구조입니다.

02 · Runtime Flow

리서치 한 건이 처리되는 과정

1

인증·요청 접수

Cognito가 발급한 JWT를 웹 서버가 검증하고, 사용자·종목·질문·언어를 실행 ID에 연결합니다.

2

대기열 등록

PostgreSQL에 사용자 소유 실행을 기록하고 SQS에는 무거운 본문 대신 runId 신호를 보냅니다.

3

워커 분석

워커가 시장·기업·재무·밸류에이션·리스크 근거를 수집하고 전문 에이전트 분석과 의장 종합을 수행합니다.

4

저장·전달

내부 상태는 SQLite가 조정하고, 근거와 결과는 S3에 보존하며, PostgreSQL의 상태·소유권을 통해 사용자 화면에 전달합니다.

03 · Data Ownership

각 저장소의 역할

같은 데이터를 무조건 중복 저장하지 않고 책임을 나눕니다.

구성요소 저장하는 것 이유 현재 상태
Cognito 로그인 계정, Google 연동, 토큰 비밀번호와 인증 보안을 애플리케이션에서 분리 운영
PostgreSQL 사용자, 이용권, 사용량, 실행·리포트·상담 소유권, 공개 상태 로그인 사용자의 서비스 데이터를 관계형으로 일관되게 관리 운영
SQS / DLQ 실행 ID 기반 작업 신호와 반복 실패 메시지 웹 요청과 오래 걸리는 AI 분석을 분리하고 순간 요청을 흡수 운영
SQLite 개별 리서치의 세부 단계, 재시도, 내부 워크플로 상태 현재 단일 호스트에서 복잡한 실행 상태를 빠르고 원자적으로 조정 EC2 로컬
S3 원문 근거, 정규화 자료, 에이전트 산출물, 최종 리포트 SHA-256 기반 아티팩트를 버전 관리하며 장기 보존 운영
EBS 공유 실행 디렉터리, 캐시, 컨테이너 간 로컬 상태 웹·워커가 동일 호스트에서 빠르게 내부 상태를 공유 EC2 로컬

04 · CI/CD

코드가 운영 서버까지 가는 과정

1. main push GitHub 저장소에 변경 반영
2. Quality pnpm install · 변경 파일 lint · production build
3. AWS OIDC 장기 액세스 키 없이 배포 Role 임시 획득
4. ECR Push 커밋 SHA를 붙인 불변 Docker 이미지 저장
5. SSM Deploy SSH 대신 Systems Manager로 EC2 배포 명령 실행
6. Health / Rollback 웹·워커 상태 확인 후 실패 시 이전 이미지 복구

05 · Infrastructure

현재 운영 스펙과 선택 이유

영역 현재 스펙 설계 의도
리전 미국 동부 버지니아 북부 · us-east-1 미국 사용자와 주요 외부 서비스에 가까운 운영 위치
애플리케이션 EC2 t3.large 1대 · Web/Worker Docker 컨테이너 초기에는 운영 단순성과 비용을 우선하고 논리적으로 역할 분리
데이터베이스 RDS PostgreSQL db.t4g.micro · Single-AZ · 20 GB gp3 관리형 백업·패치의 이점을 가져가되 초기 고정비 절감
네트워크 VPC · 2개 Public Subnet · Elastic IP · Nginx NAT Gateway와 ALB 비용 없이 단순하게 시작
내구성 RDS 7일 백업 · S3 버전 관리 · 암호화 저장 사용자 데이터와 리서치 근거의 최소 복구 기반 확보
보안 RDS 비공개 · SG 제한 · S3 Public Block · IMDSv2 · IAM Role 인터넷에 DB·S3를 직접 노출하지 않고 최소 권한으로 접근

06 · Evaluation

현재 구조의 장점과 한계

장점

  • 웹 요청과 장시간 리서치를 SQS와 워커로 분리했습니다.
  • 인증·관계형 데이터·파일 보존을 AWS 관리형 서비스에 맡겼습니다.
  • 동일 이미지로 웹·워커를 배포해 환경 차이를 줄였습니다.
  • OIDC, ECR 불변 태그, 상태 검사, 자동 롤백이 배포 위험을 낮춥니다.
  • 초기 트래픽에서는 ALB·NAT·다중 서버 비용을 피할 수 있습니다.

현재 한계

  • EC2 한 대가 멈추면 웹과 워커가 동시에 영향을 받는 단일 장애점입니다.
  • 내부 실행 상태가 로컬 SQLite에 있어 수평 확장의 핵심 제약입니다.
  • RDS가 Single-AZ라 장애 자동 전환보다 비용 절감을 우선한 상태입니다.
  • 현재 기본 동시 실행 수가 작아 사용량 급증 시 대기열이 길어질 수 있습니다.
  • 중앙 로그·지표·알람과 EBS 자동 스냅샷은 다음 운영 보강 항목입니다.

07 · Scale Path

사용량 증가 시 확장 순서

한 번에 전면 교체하지 않고 병목 순서대로 확장합니다.

관측성 보강

CloudWatch 로그·지표·알람, 비용 알림, EBS 스냅샷을 먼저 추가합니다.

상태 외부화

SQLite 워크플로 조정 상태를 PostgreSQL 또는 별도 상태 저장소로 이전합니다.

웹·워커 분리

리서치 워커를 별도 EC2/ECS로 늘려 대기열 길이에 따라 처리량을 확장합니다.

고가용성

ALB, Auto Scaling, Multi-AZ RDS를 적용해 단일 장애점을 제거합니다.
